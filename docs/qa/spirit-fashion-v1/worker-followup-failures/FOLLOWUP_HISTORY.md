# 최종 Worker 검증 전 실패와 대조

최상위 `README.md`와 여섯 원본 파일은 Room 버퍼 누락을 발견한 당시의 기록이다. 그 파일의 원래 SHA manifest를 유지한다. 최신 결과는 [worker-final](../worker-final/README.md)이며 아래 실패를 지우거나 PASS로 바꾸지 않았다.

1. **Room instanceMatrix 누락**: 원래 Worker `53cf7d83…`의 첫 종료에서166 생성/165 delete 호출/미해제1개가 검출됐다. 첫 report와 creation-stack report/harness를 그대로 보존한다. 원래 보고서의96 floats/384 bytes는 소스에서 추론한 값이며 native bufferData 또는 종료 전 liveness를 측정한 값이 아니었다. root의 공유 수정 `5a8fae1`은 실제 Room InstancedMesh.dispose를 기존 Room.dispose 전에 호출한다. 최신 검사에서는 첫 PMREM 이전부터 실제96/384 업로드·원본 SHA·live→한 번의 실제 delete→false와 정상 강제 context loss 전 native live0을 확인한다. 이전 소스 harness의4,787/4,787 계측은 환경 생성 후 설치해 이 버퍼를 포함하지 않았다.
2. **원시300ms 첫 실패**: `300ms-first/`의 Worker `cbe4bf8a…`/harness `c881b4b4…`는 고품질 다섯 십간10착용을 통과한 뒤 己 마스크 교체의 원시300ms 제한에 실패했다. 그 harness는 실패한 snapshot/정확한 시간값을 보존하지 않았으므로 값이 있었다고 주장하지 않는다. 원래 보고서·harness·당시 PNG6개를 보존한다.
3. **원시300ms 재현과 측정**: `300ms-diagnostics/`의 harness `0d4740b9…`는 같은 소스/Worker에서 실패 snapshot을 남겼다. 己 교체747.5ms 중 추가 QA native 조회739.7ms, 조회 외 동기 wall-time7.8ms였다. 추가 getError만 제거한 `timing-geterror-probe/`에서는 기다림이 남은 isBuffer 조회로 옮겨갔다. 둘을 synchronous fashion.set 안에서만 제외한 `timing-all-query-probe/`의 같은 교체는5.6–8.6ms였다. 이 대조에서는 생략한 liveness를 null로 남기며 strict native 소유권 증거라고 해석하지 않는다. 제품 코드를 바꾸지 않았다.
4. **최종 시간 정의**: 최종 harness는 추가 조회를 모두 다시 켰다. bound real wall clock으로 raw·disjoint query·exclusive 시간을 함께 기록하고, 중첩 조회0·exclusive 음수0·exclusive300ms 미만을 검사한다. 제품의 native delete와 나머지 계측 작업은 exclusive 값에 포함된다. 최종 matrix180샘플 최대exclusive18.1ms, 원시690.1ms/300ms 초과3개다. 원시300ms가 통과했거나 processor-time/실제 기기 반응 시간을 측정했다고 주장하지 않는다. 원래 실패 기준과 결과를 그대로 유지한다.
5. **controlled-rAF 종료 대기 timeout**: `view-unmount-timeout/`의 harness `e2521707…`는 고품질20착용/10원본 손 인사/UI·저장·착용 context 복구를 통과한 뒤 실제 화면 전환의 waitForFunction에서 timeout이 났다. 원래 report/harness/PNG12개를 보존한다. `unmount-polling-probe/`는 동일 조건이 처음 false, 기본 대기 timeout 직후 true였고 Playwright의 `next` callback이 멈춘 synthetic rAF에 대기 중임을 확인했다. 숫자 polling25ms는 같은 조건을 통과했다. 이 대조의 aggregate466/466 delete 호출과 복구된 현재 유효 generation1의233/233 explicit native delete/live0을 구분한다.
6. **최종 재실행**: 숫자 polling을 세 condition wait에 적용한 실행 harness `cec27692…`가 동일 제품 소스/Worker에서28/28개·40착용·PNG17개를 통과했다. condition, native draw/attributes/alpha/error, Room 소유권, 같은 시간 복구와 정상 강제 loss 전 explicit delete/live0 검사는 유지했다. 최종 복구 후 종료의 현재 generation1은 각 품질215/215 explicit native delete/live0이고, lost generation을 포함한430/430 delete 호출은 별도 값이다.

`followup-sha256-manifest.json`은 이 후속 파일들에 대한 별도 manifest다. 최초 여섯 파일의 `sha256-manifest.json`은 변경하지 않았다. 모든 시각/시간 측정은 로컬 Chromium SwiftShader와 synthetic D1/헤더 범위이며 패션은 배포하지 않았다.
